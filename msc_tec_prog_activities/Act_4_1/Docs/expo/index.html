01

Arquitectura utilizada

Se decidió utilizar la arquitectura MVR (Modelo · Vista · Repositorio).

  • Separación de responsabilidades

    Si cambias de MySQL a otra base de datos, solo tocas el Repositorio. La Vista no cambia.

  • Menos código repetido

    El SQL está en un solo lugar, no disperso en cada botón.

  • Fácil de probar y leer

    Cada archivo hace una sola cosa.

02

Configuración de carpetas

  • domain Modelo

    Define las clases Cliente, Cuenta (ahorro) y CuentaCredito con sus atributos. Son objetos simples que viajan entre las capas; no saben nada de la base de datos ni de la interfaz.

  • repositories Repositorio

    Es el único lugar del programa que contiene SQL: altas, bajas, cambios y consultas. Usa la conexión de db y convierte cada fila en un objeto de domain, así el resto del código nunca escribe una consulta.

  • ui Vista

    Ventanas, formularios y tabla diseñados en Qt Designer (archivos .ui). Solo muestra datos y recibe acciones del usuario; para cualquier operación llama a services, nunca a db directamente.

  • services Negocio

    Contiene las reglas del banco: depósitos, retiros y validaciones de saldo y límite de crédito. Decide si una operación es válida antes de pedir al repositorio que la guarde.

  • db Infraestructura

    Connection.py abre la conexión a MySQL leyendo las credenciales del archivo .env. Incluye script.sql, que crea la base de datos BankAccounts y sus tablas.

  • utilities Apoyo

    Funciones reutilizables que no pertenecen a una sola capa: validación de los campos de los formularios y lectura/escritura de archivos CSV y XLSX.

  • data Archivos

    Archivos .csv y .xlsx que el programa importa para cargar cuentas o exporta al guardar reportes.

  • icons Recursos

    Imágenes que usan los botones y ventanas de la interfaz, separadas del código para cambiarlas sin tocarlo.

04

Modelo de datos

Como mejora, se separó al cliente de sus cuentas: en un banco real una persona puede tener varias cuentas de ahorro y de crédito.

client

  • PKid
  • paternal_surname
  • maternal_surname
  • name
1 : N

account

  • PKaccount_number
  • FKid_client
  • balance
  • created_at
1 : 0..1

credit_account

  • PK FKaccount_number
  • credit_limit
  • debt
  • Herencia en dos niveles: en Python CreditAccount hereda de Account; en MySQL la tabla credit_account extiende a account con la misma llave.
  • El número de cuenta ya no se pide: lo genera AUTO_INCREMENT a partir de 1000, como en un banco real.
  • La base protege los datos: CHECK (balance >= 0), CHECK (debt <= credit_limit) y ON DELETE CASCADE para no dejar registros huérfanos.
05

Reglas del banco

Todas viven en services/account_service.py; la Vista solo muestra el resultado o el mensaje de error.

  • Depósito

    El monto debe ser mayor a 0. En una cuenta de crédito con adeudo, el depósito primero paga el crédito y el resto va al saldo.

  • Retiro de ahorro

    Solo si el monto es menor o igual al saldo; si no, se muestra un mensaje.

  • Retiro de crédito

    Se retira primero del saldo y lo que falte se toma del crédito. Se rechaza si excede saldo + crédito disponible.

  • Cambiar límite

    El nuevo monto de crédito no puede quedar por debajo del adeudo actual.

07

Decisiones técnicas

  • Decimal

    Todas las cantidades se manejan con Decimal, no con float, para que $0.10 + $0.20 sea exactamente $0.30.

  • Transacciones

    Crear un cliente con su cuenta o editar ambos va en una sola transacción: si falla una parte, se hace rollback de todo.

  • Validar primero

    Los servicios construyen y validan los objetos antes de tocar la base de datos; los errores llegan a la Vista como mensajes claros.

  • .env

    Las credenciales de MySQL se leen de un archivo .env con python-dotenv; no están escritas en el código.

  • Importación segura

    Al importar se conserva el número de cuenta del archivo, así un archivo exportado se puede volver a cargar sin duplicar cuentas. Acepta fechas de texto y de Excel.
